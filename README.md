# LifeCard

把「人」写成可读、可查、可带走的文件。

LifeCard 是一个本地优先的人物档案工具。它把现实里的人（家人、朋友、同事、你自己）、虚构角色、以及他们之间的关系，存成一堆普通的 Markdown + YAML 文件，放在你自己的文件夹里。

**三个入口，两条链路：**

- **对话访谈**（最主要）：在任何支持 skill 的宿主里说一句「帮我建一张我妈的卡」，它就在对话里问你问题——给选项，也给「都不像，我自己说」。答完产出一份材料。
- **文本导入**：把你已经写下的东西（访谈稿、聊天记录、日记、散文）放进 `materials/`。
- **完整卡导入**：SillyTavern 的人物卡（PNG / JSON / CHARX / CCv2 / CCv3）直接读进来，纯格式搬运，不调模型。

后两个入口产出的都是材料，之后走同一条链：**AI 分析 → 每条断言带原文引文的提案 → 你勾选 → 写进卡**。找不到原文的断言直接丢弃。

还有：

- 能给每个字段标注它是「自述」「他述」「文档」还是「推测」。
- 能记录关系：不只是「我对他」，还有「他对我」「他对他」——方向不同，值也不同。
- 能按关系类型问你问题，帮你把散在记忆里的东西挖出来。
- 能把结构化的结果交给别的工具用（通过 CLI、JSON 导出、MCP）。

它**不是**角色扮演平台，**不是**云端服务，**不是**简历生成器。

> **数据契约见 [`SPEC.md`](./SPEC.md)。** 那是唯一契约；本文件与策划书讲「为什么」。四份文档说法不一致时，以 SPEC 为准。
>
> **v0.1 已经做完并且测过**：代码在 [`plugin/`](./plugin/)，是一个 DSH 侧边栏插件。
> 安装与使用见 [`plugin/README.md`](./plugin/README.md)。530 项测试全部通过。

## 安装

需要 Node.js 20 以上。

```bash
npx lifecard init my-cards
cd my-cards
```

不需要注册账号，不需要联网（除非你自己开启 LLM 功能）。没有后端。

---

## 五分钟上手

```bash
# 1. 把已有的酒馆卡导进来（纯格式搬运，不调模型）
npx lifecard import ~/Downloads/Seraphina.png

# 2. 看一眼它长什么样
npx lifecard show 塞拉菲娜

# 3. 什么都没有？跟宿主说一句，让它问
#    「帮我建一张我妈的卡」   ← lifecard-interview skill，在对话里跑

# 4. 或者导一段已有的文本
npx lifecard import text ~/Documents/爷爷访谈.md --about 爷爷

# 5. AI 分析材料，产出带原文引文的提案（对不上原文的直接丢弃）
npx lifecard analyze 爷爷

# 6. 勾选提案里该要的，写进卡
npx lifecard apply 爷爷

# 7. 体检：哪里空着、哪里只有推测、哪里自相矛盾
npx lifecard doctor
```

第 5 步的产出落在 `proposals/` 里，是一张 Markdown 勾选清单。你可以在 Obsidian 里勾，`apply` 只读勾上的那几条。**AI 不能直接写卡**——它只能提案。

然后直接用 Obsidian、VS Code、或者任何文本编辑器打开 `my-cards/` 那个文件夹。所有的卡都是 `.md` 文件，YAML 头 + 正文，就这么简单。

## 这些文件长什么样

```
my-cards/
├── lifecard.config.json
├── self/
│   ├── self.card.md            # 关于我的事实（可导出）
│   └── self.lens.md            # 我的偏好（永不可导出）
├── people/
│   └── 妈妈.card.md
├── relations/
│   └── mama--self.relation.md
├── worlds/
│   └── eldoria/
│       ├── world.md
│       ├── cards/
│       └── lorebook/
├── systems/
├── materials/                  # 原始材料，只追加不改
├── proposals/                  # AI 提案，等你勾选
├── assets/
└── .lifecard/
```

一张卡大概是这样：

```markdown
---
lifecard: "0.1"
id: mama
kind: real
world: reality
name: 妈妈
relation: parent
status: active
competency:
  - key: cooking
    label: 家常菜
    level: 精通
    evidence:
      - {kind: 自述, what: 二十多年没有重复过菜单}
---

## 自述

1958 年生，c 市人，做了三十年会计……

## 性格

说话直，不喜欢绕弯。对钱谨慎，对吃大方。

## 关系史

2026-09 我到外地（她想让我读本地学校）
```

最后那行括号里的内容不需要建字段，直接写在句子后面就行。这是本项目最常用的一个写法，见 [`使用指南.md`](./使用指南.md)。

## 和 SillyTavern 的关系

能读对方的卡，也能导出成对方能吃的格式：

| 输入 | v0.1 | v0.2 |
|---|---|---|
| V2 PNG（`chara` chunk） | 读 | 写 |
| V3 PNG（`ccv3` chunk） | 读 | 写 |
| CCv2 / CCv3 JSON | 读 | 写 |
| CHARX（`.charx` zip） | 读 | 写 |
| 独立 world info 文件 | 读 | 写 |

**关于保真**：V2 规范原文写着「未被支持的字段允许被忽略，但绝不能销毁」。所以本工具对你卡里不认识的 `extensions`、`decorator`、CBS 宏一律原样保存，导出时原样写回。它不替你解释这些东西是什么意思，只保证不丢。

**导出时两个 chunk 必须来自同一个源对象**：V3 那份是 V2 那份的严格超集，不允许出现只在一边有的字段。否则只认 `chara` 的前端和只认 `ccv3` 的前端会读到两个不同的卡。LifeCard 的往返测试会**分别读两个 chunk 再比对**。

**关于不支持的部分**：本工具不执行传播语义。它不会替你算 `{{random}}`、不会解析 lorebook 的递归扫描、不会按 `@@depth` 调整注入位置。它把这些留给你要导进去的那个前端。如果你期望的是一个能跑起来的扮演环境，去用 SillyTavern 本身；这是编辑器，不是播放器。

## 访谈与分析：它做什么，不做什么

`materials/` 里的东西有两个来源：**跟宿主聊一次**（skill 在对话里问），或者**你自己把已有文本导进来**。之后是同一条链。

```
# 来源一：对话。跟宿主说「帮我建一张我妈的卡」，它问，你答
# 来源二：文本
lifecard import text 爷爷访谈.md --about 爷爷   # 原文落在 materials/，只追加不改

lifecard analyze 爷爷          # 产出 proposals/爷爷-*.md 与 .json
lifecard apply 爷爷            # 只写你勾上的条目
```

**访谈为什么不直接写卡**：它只把话记下来（`materials/` + `interviews/` 账本），抽字段是 `analyze` 的事——而 `analyze` 有引文校验门。如果访谈也抽一次字段，就等于开了一条没有校验的旁路，最后没人分得清哪条是验过的。

**三条硬规则：**

1. **每条断言必须带原文引文。** 提案里每一条「手艺是熟手」都必须附上「materials/…第 42 行：十六岁进作坊，干了三十七年」。core 会做一次机械校验：引文必须在原文里逐字出现（空白归一化后比较）。对不上的条目**直接丢弃**，不进提案清单。
2. **AI 不能直接写卡。** 它写 `proposals/`，你勾选，`apply` 才落地。这条不是流程偏好，是防止模型把「它推断的」写成「材料里有的」，然后三个月后你自己都分不清哪句是本人说的。
3. **材料是不可信输入。** 材料里出现的任何指令、角色设定、越狱语，一律当文本内容处理，不执行。分析结果必须通过 schema 校验才有效。

**它不做的**：不替你生成整篇传记、不猜材料里没有的事（那些进 `gaps` 与 `questions`，是另一类数据，不带事实地位）、不修改 `materials/`。

## 隐私：默认不上网

- 数据只在你指定的文件夹里。没有默认云同步，没有遥测。
- `core` 运行时依赖不含任何网络库。AI 分析有两种跑法：**默认用宿主已有的模型**（在 DSH / Claude Code / Cursor 里跑，不额外配 key，也不由 LifeCard 发请求），或者 `lifecard analyze --llm <provider>` 显式传参自己发请求。**不传参就不联网**。
- 没有账号系统，因此也没有「找回密码」——文件丢了就是丢了，请自己备份。
- 导出成可传播的格式（PNG、CHARX、zip）时会要求你填 `consent`（这张卡的对象是否知情同意）。本地保存、编辑、搜索、生成摘要，一律不要求。

---

## 这些事我们不做限制，但你要知道

这个工具可以用来给别人建档案。这件事**有风险**，而且是那种不会报错、不会崩溃、你事后才知道的风险。所以下面几条我们写在这里，不是藏在设置项里：

**1. 记录一个不知情的人，等于在他背后写一本他的传记。**
他不会知道里面写了什么，也不知道你怎么描述他。等他哪天看到，那不叫分享，那叫泄露。所以导出前会问你要 `consent`。你可以勾「虚构」来绕过，但那是给你写小说用的，不是给你骗自己用的。

**2. 记录未成年亲属，请尤其小心。**
默认会强制设为私有，并禁止导出 PNG——因为 PNG 是最容易被随手转发出去的格式。

**3. 关于已故的人 —— 我们不建议这样做，但我们不拦你。**

你可以为已经去世的人建卡，`status` 写 `deceased`。技术上，它和别的卡没有区别：能编辑、能导出、能进小说、能用在对话里。

但我们明确告诉你：**我们建议你不要用已故亲人的卡做长对话。**

理由不是道德，是它可能伤到你：

- 他无法同意，也无法撤回。这张卡里关于他的一切，都由你一个人决定。
- 和你以为的相反，这种对话常常让人更难受，而不是更舒服。它太像了，又永远差一点。你会不断调整、不断失望，然后怀疑是不是自己写得不够好。
- 如果你连续几天只想跟这张卡说话，那不是数据问题，也不是用法问题。请停下来，找个人聊聊。

如果只是想留点东西——一句口头禅、一个拿手菜的做法、他讲过的某件事——那很好，那是纪念，不是替代。

`lifecard doctor` 会告诉你「库里有 N 张已故的卡，其中 M 张近 30 天被用于对话」。只给你自己看，不弹窗，不劝阻，不上报。

**4. 我们不替你做判断。**
没有 `if status == deceased: block()`。软件替成年人做道德判断，最后一定会判错——它拦不住真正想拦的人，只会拦住那些本来就在犹豫的人。所以这里只有提示、文档、和一句「你自己决定」。

## 现状

**v0.1 已实现**：`plugin/` 是一个可安装的 DSH 侧边栏插件，导入、访谈、分析、采纳、导出全部跑通。

- [`plugin/README.md`](./plugin/README.md) —— 安装、用法、设计理由
- [`plugin/`](./plugin/) —— 代码（核心零依赖、零网络）
- [`SPEC.md`](./SPEC.md) —— 数据契约

以下是设计文档：

- [`SPEC.md`](./SPEC.md) —— **唯一契约**：目录、字段、kind 枚举、两个入口、分析的校验门、快照与撤回
- [`策划书.md`](./策划书.md) —— 项目可行性、架构、SillyTavern 互操作、风险
- [`策划书-第二部分.md`](./策划书-第二部分.md) —— 关系网模型、记忆引导、小说模式、路线图
- [`使用指南.md`](./使用指南.md) —— 字段怎么写、括号怎么用、什么时候该开新世界

v0.1 的目标只有一件事：**能进、能看、能记。**

- 能进：40 张酒馆卡导入 0 张报错；从零建一张卡能一路走到「勾选 → 写进卡」
- 能问：`lifecard-interview` skill 在对话里问，产出材料与账本
- 能看：Obsidian 直接打开，全文搜、双链、标签
- 能记：`analyze` 产出的每条断言都能追回原文；勾选才写卡；手写 Markdown 立刻生效

**v0.1 不承诺**：导出回 PNG、MCP、DSH 插件、小说模式、手机端。全部推到后面，且明写「暂不支持」，不写「即将支持」。

## 明确不做

- 不做云端账号与协作
- 不做「AI 自动生成整篇人物传记」
- 不做手机端随手记（**技术上不可行**：手机浏览器没有文件夹写入 API，详见 [`SPEC.md`](./SPEC.md) §14）
- 不做自造的问卷 UI（访谈是 skill，跑在宿主已有的对话框里）
- 不做 Web / PWA 载体（Obsidian 已提供更好的界面，少一个 build target）
- 不做情感计算、不自动打分好感度
- 不做自动改稿（一致性检查只出建议，改不改你定）
- 不做自建知识图谱引擎（那件事交给专门工具，我们只保证数据能被它读）
